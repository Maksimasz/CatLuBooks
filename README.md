# CatLuBooks

**Русский** · [English](README.en.md)

RAG-ассистент по документам: ищет ответ в ваших книгах/файлах и отвечает,
ссылаясь на источник и страницу. Веб-интерфейс работает и на ПК, и на телефоне
(как приложение через PWA).

**Быстрые ссылки:** [руководство для новичка](docs/РУКОВОДСТВО.md) ·
[установка](#установка-install) ·
[перенос на другой компьютер](#перенос-на-другой-компьютер-migration) ·
[подготовка базы](#подготовка-базы) · [настройка](#настройка-configyaml)

## Как это работает

```
книга (PDF, EPUB, TXT, FB2) ─► текст ─► фрагменты ─► эмбеддинги ─► база (ChromaDB)
                                                       │
вопрос ─► поиск (вектор + точные совпадения) ──────────┤
                                                       ▼
                             контекст + вопрос ─► LLM ─► ответ со ссылками
```

- **Эмбеддинги** считаются локально (модель маленькая, интернет не нужен).
- **Генерация** — через любой OpenAI-совместимый сервер: Ollama, LM Studio,
  llama.cpp, а также облако (OpenAI, OpenRouter, Groq, DeepSeek).

## Возможности

- **Агенты**: у каждого своя папка, свои книги, своя база и свой промпт —
  знания разных тем не смешиваются (например «Документы» и «Заметки» рядом).
- Всё управление из интерфейса (⚙ в правом верхнем углу): создать агента,
  загрузить и удалить книги, запустить индексацию, ввести ключ и выбрать модель.
  К консоли и проводнику обращаться не нужно.
- Индексация книг пачками, без загрузки всей книги в память; идёт в фоне и
  показывает ход работы.
- Сканы: сервер сам проверяет, есть ли в PDF текст, и предлагает включить OCR
  (нужен установленный Tesseract с русским языком) прямо в настройках.
- Гибридный поиск: векторный + приоритет точных совпадений; к ответу
  добавляются соседние фрагменты и номер страницы (или раздела).
- Сведение: один и тот же материал, найденный в нескольких книгах, собирается
  в один связный ответ (быстрый и точный режимы — переключателем).
- Перед ответом модель анализирует найденное: что важно, есть ли
  противоречия или пробелы — и только потом отвечает.
- Потоковый ответ (текст «печатается» по мере генерации).
- Веб-чат + PWA: ставится на телефон как приложение.
- Управление сервером из админки (⚙ → Сервер): адрес для телефона, перезапуск
  (после правки `config.yaml` или `git pull`) и остановка. Запускать остановленный
  сервер можно только на компьютере.
- Всё сменное — в одном файле `config.yaml` (тема, модель, промпты, размеры
  фрагментов).

## Агенты

```
agents/
└── dokumenty/          # агент: папка с латинским именем
    ├── agent.json      # название, описание и свой промпт агента
    ├── books/          # книги агента (загружаются из интерфейса)
    └── db/             # база этого агента (ChromaDB)
```

Папка агента самодостаточна: скопировали папку — перенесли агента вместе с
книгами и базой на другой компьютер; удалили папку в интерфейсе — удалили
агента целиком. Имя папки делается латиницей из названия («Документы» →
`dokumenty`), при совпадении названий добавляется номер (`dokumenty-2`).

Папка `agents/` не попадает в git: это ваши книги и базы.

### Промпт агента

Промпт у каждого агента свой. При создании вы указываете не только название, но
и тему — что за документы внутри, и по этой теме модель пишет системный промпт:

- агент по даташитам получает промпт про распиновку, допуски и пайку;
- агент по договорам — про пункты, сроки и ссылки на статьи;
- агент по кулинарным книгам — про ингредиенты и порядок приготовления.

Промпт хранится в `agent.json` вместе с названием:

```json
{
  "title": "Документы",
  "description": "даташиты разъёмов и инструкции по пайке",
  "prompt": "Ты — ассистент по технической документации…",
  "created": "2026-10-20 12:00"
}
```

Правка — ⚙ → Агенты, поле «Промпт агента»: «Сохранить» записывает текст,
«Составить заново» просит модель написать промпт по теме, указанной рядом.
Тема тоже сохраняется, чтобы при следующем составлении модель знала контекст.

Промпт составляется сразу после создания агента, но в фоне: книги можно
загружать и индексировать, не дожидаясь ответа модели (локальной модели на CPU
нужна на это минута, облачной — секунды).

Если модель недоступна (нет ключа, Ollama не запущена), агент всё равно
создаётся: промпт берётся из шаблона `prompt.agent_default_system`, а причина
видна в интерфейсе. Пустой промпт — работать по общему `prompt.system` из
`config.yaml` (так продолжают работать агенты, созданные до появления своих
промптов).

```
│   ├── server.py       # адреса в сети, перезапуск и остановка сервера

├── agents/             # агенты: книги и базы (не в git)
├── models/             # GGUF-модели для llama.cpp (не в git)
├── settings.json       # выбор из интерфейса, например OCR (не в git)
├── secrets.json        # ключи облачных провайдеров (не в git)
├── tests/              # автономные тесты (без Ollama и моделей)
├── requirements.txt
└── LICENSE
```

## Установка (install)

### Что понадобится

| Что | Зачем | Где взять |
|---|---|---|
| Python 3.10+ | запускает сервер | <https://www.python.org/downloads/> — либо не ставить вовсе: uv скачает сам |
| uv (не обязательно) | сам скачает Python и поставит зависимости | <https://docs.astral.sh/uv/> — команда установки в шагах ниже |
| Модель эмбеддингов | поиск по книгам (локально, в облако не уходит) | скачается сама при первом запуске — [paraphrase-multilingual-MiniLM-L12-v2](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2) |
| Ollama и модель генерации | ответы на этом ПК, без облака | [ollama.com/download](https://ollama.com/download), модели — [поиск](https://ollama.com/search) |
| Ключ облачного провайдера | если ответы делает облако | таблица «Провайдеры моделей» ниже |
| Tesseract с русским языком | чтение сканов, если они есть | [установщик UB-Mannheim](https://github.com/UB-Mannheim/tesseract/wiki) |

Интернет нужен один раз — скачать зависимости и модели. Дальше всё работает локально.

### Шаги

```bash
git clone https://github.com/Maksimasz/CatLuBooks.git
cd CatLuBooks
ollama pull yandex/YandexGPT-5-Lite-8B-instruct-GGUF   # модель генерации, или другая
```

Дальше — как удобнее: через **uv** (он сам скачает нужный Python, поставит
зависимости и запустит; активировать окружение не нужно) или обычными
`venv` + `pip`.

**Через uv** — [uv](https://docs.astral.sh/uv/) ставится одной строкой:

```bash
# если uv ещё нет (Windows):
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
# Linux/macOS: curl -LsSf https://astral.sh/uv/install.sh | sh

uv venv --python 3.12             # Python скачается сам, если его нет в системе
uv pip install -r requirements.txt
uv run python app.py
```

Запуск и в дальнейшем такой же: `uv run python app.py` — uv сам находит `.venv`
в папке проекта. Обновить зависимости: `uv pip install -r requirements.txt`.

**Через venv и pip**:

```bash
python -m venv .venv
.\.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt   # около гигабайта: torch и остальное
python app.py
```

Откройте <http://localhost:8000> — дальше всё делается в интерфейсе (⚙).

Что происходит при первом запуске:

- скачивается модель эмбеддингов (~120 МБ) в кэш HuggingFace пользователя — это
  единственный момент, когда поиску нужен интернет. Готовая папка кэша
  (`%USERPROFILE%\.cache\huggingface`) переносится на другой ПК без сети;
- если модели из `llm.model` на этом ПК нет, ответы генерироваться не будут:
  выполните `ollama pull <модель>` (или выберите другую в ⚙ → Модели);
- проверка, что всё на месте: `python -m unittest discover -s tests -t .` —
  тесты автономные, ни моделей, ни Ollama не требуют.

### Обновление

```bash
git pull        # затем перезапустите сервер: ⚙ → Сервер → Перезапустить,
                # либо Ctrl+C и python app.py
```

Обновление не трогает ваши данные: книги и базы лежат в `agents/`, ключи — в
`secrets.json`, настройки из интерфейса — в `settings.json`. Если вы правили
`config.yaml`, при обновлении возможен конфликт — сохраните свою копию заранее.

## Перенос на другой компьютер (migration)

Переезд — это копирование нескольких папок. Переустанавливать зависимости и
заново индексировать книги не нужно, если перенести базу.

### Что копировать

| Папка или файл | Что это | Нужно ли |
|---|---|---|
| `agents/` | книги и готовые базы агентов — самое ценное | да, если нужны ваши книги |
| `secrets.json` | ключи облачных провайдеров (Groq, OpenRouter…) | если пользуетесь облаком |
| `settings.json` | выбор из интерфейса: OCR, режим сведения | нет, настроится заново |
| `config.yaml` | ваши правки настроек | если меняли |
| кэш HuggingFace | модель эмбеддингов (~120 МБ) | нет, скачается сама |

`agents/` растёт вместе с библиотекой: у агента с несколькими десятками книг
база занимает единицы гигабайт. В git эти файлы не попадают, поэтому переносить
их нужно вручную — флешкой, по сети или архивом.

### Порядок действий

1. На новом компьютере выполните шаги из раздела «Установка».
2. Скопируйте `agents/` (и, если нужно, `secrets.json`, `settings.json`,
   `config.yaml`) в корень проекта — туда же, где лежит `app.py`.
3. Запустите сервер: `python app.py` (или `uv run python app.py`).
4. Для локальных ответов скачайте модель: `ollama pull <модель>` — какую
   выбрать под железо нового компьютера, подскажет раздел
   [«Подбор модели под слабое железо»](#подбор-модели-под-слабое-железо).
5. В браузере выберите провайдера и модель: ⚙ → Модели. Этот выбор хранится
   в браузере, а не в файлах проекта, поэтому на новом компьютере его нужно
   сделать заново. Ключ облака удобнее ввести там же кнопкой «🔑 Ввести
   API-ключ» — тогда `secrets.json` копировать не обязательно.
6. Откройте агента: книги, фрагменты и история поиска уже на месте.

Нажимать «Индексировать» после переноса не нужно — база лежит в
`agents/<агент>/db` и готова к поиску.

### Если переносите только книги

Скопируйте `agents/<агент>/books` (или создайте агента и загрузите книги через
интерфейс) и нажмите ⚙ → Книги → «Индексировать». Это надолго: индексация
десятков книг занимает часы. Если среди книг есть сканы, на новой машине
понадобится Tesseract с русским языком.

Повторная индексация после копирования перечитает книги: у файлов меняется
время изменения, а по нему индексация понимает, что книгу пора перечитать.
Готовой базе это не вредит — просто не запускайте индексацию, если база уже
перенесена.

### Что важно не менять

Модель эмбеддингов (`embeddings.model` в `config.yaml`) должна остаться той
же, с которой собрана база: векторы разных моделей несравнимы, и поиск начнёт
выдавать случайные фрагменты. Если модель всё-таки сменили, пересоберите базу
целиком: ⚙ → Книги → «Всё заново».

Пути внутри базы относительные (`инструкции/руководство.pdf`), поэтому перенос не
зависит от того, куда положен проект, и работает между Windows и Linux.

## Подготовка базы

Агенты и книги создаются прямо в интерфейсе — откройте <http://localhost:8000>
и нажмите ⚙ в правом верхнем углу:

1. **Агенты** — создайте агента (например «Документы»). Появится папка
   `agents/dokumenty/` со своим `books/` и своей `db/`.
2. **Книги** — загрузите файлы (PDF, EPUB, TXT/MD, FB2; подпапки в `books/`
   тоже читаются) и нажмите **Индексировать**. Ход работы виден на месте:
   какая книга читается и сколько фрагментов уже записано. Индексация идёт в
   фоне — настройки можно закрыть и продолжать общаться в чате.
3. **Модели** — выберите провайдера и модель, при необходимости введите ключ.

Книгу можно удалить в том же окне: файл и его фрагменты убираются вместе.
Повторная индексация обновляет уже добавленные книги, а не дублирует их.

Уже прочитанные книги при повторном нажатии «Индексировать» пропускаются:
читаются только новые и изменённые. Поэтому добавить одну книгу — это минуты,
а не часы: в списке видно «уже в базе, читать заново не нужно». Прочитать всё
заново (например, чтобы заново распознать сканы) можно кнопкой **Всё заново** —
она сначала спросит подтверждение.

Если файл убрали из папки мимо интерфейса, его фрагменты остаются в базе. Такая
строка видна в списке книг с пометкой «нет файла», и её можно убрать тем же 🗑 —
тогда из базы уйдут оставшиеся фрагменты.

Индексацию можно запустить и из консоли (например, если база собирается на
сервере без графики):

```bash
python -m core.database              # проиндексировать всех агентов
python -m core.database dokumenty    # одного агента
```

Страницы PDF читаются текстовым слоем; EPUB, TXT/MD и FB2 текстовые по своей
природе. Сканы (страницы-картинки) распознаются через Tesseract — об этом ниже.
Файлы `.djvu` и `.mobi` не читаются: нужен конвертер.

### Сканы и OCR

Если книга — это фотографии страниц, текста в ней нет, и в базе искать будет
нечего. Сервер проверяет книги сам: у такого PDF в ⚙ → Книги появляется
пометка «скан», а под переключателем — подсказка включить OCR.

Распознавание делает [Tesseract](https://github.com/UB-Mannheim/tesseract/wiki) —
отдельная бесплатная программа. Порядок:

1. Установите Tesseract для Windows (установщик UB-Mannheim). При установке
   раскройте «Additional language data» и отметьте **Russian** — без него
   русский текст не распознаётся.
2. Откройте ⚙ → Книги и нажмите «Проверить снова»: сервер найдёт программу
   сам (он смотрит и в PATH, и в `C:\Program Files\Tesseract-OCR`),
   перезапускать его не нужно.
3. Включите «Распознавать сканы» и нажмите «Индексировать».

Что важно знать:

- OCR нужен только для PDF-сканов; в EPUB/FB2/TXT текст уже есть.
- Скорость — около 1–2 секунд на страницу: книга на 300 страниц займёт
  5–10 минут. Работа идёт в фоне, настройки можно закрыть.
- Качество зависит от скана: ровный текст распознаётся почти без ошибок,
  таблицы в две колонки и мелкий шрифт — хуже.
- Настройка хранится локально в `settings.json` (в git не попадает) и важнее
  строки `store.ocr` в `config.yaml`.
- Книги, которые уже лежали в базе без OCR, перечитываются сами: после
  включения распознавания нажмите «Индексировать» — сервер увидит, что скан
  прочитан без распознавания, и прочитает только его, обычные книги не тронет.

### Убрать данные из базы

Обычно это делается в интерфейсе (⚙ → Книги, ⚙ → База). Из консоли:

```bash
python tools/drop.py --list                   # агенты, книги и фрагменты
python tools/drop.py dokumenty                # что внутри одного агента
python tools/drop.py dokumenty "Руководство.pdf"   # убрать книгу вместе с фрагментами
python tools/drop.py dokumenty --clear        # очистить базу агента
python tools/drop.py dokumenty --delete       # удалить агента целиком
```

Перед этим остановите сервер (`Ctrl+C`): он держит базу открытой. Чтение
(`--list`) работает и при запущенном сервере.

Из интерфейса останавливать сервер не нужно: удаление в ⚙ → Книги (🗑) и
очистка базы работают на ходу — сервер сам закрывает базу. Остановка
(`Ctrl+C` или ⚙ → Сервер → Остановить) нужна только для консольной утилиты
`tools/drop.py` и для полной остановки сервера. Строка «нет файла» — это
фрагменты книги, файл которой удалили мимо интерфейса: 🗑 у такой строки
убирает только фрагменты из базы.

Удаление книги (🗑) бывает двух видов, чтобы не терять знания по ошибке:
- 📄 **«Удалить только файл»** — файл убирается с диска, а фрагменты в базе
  остаются: знания продолжают искаться, просто источник больше не откроется.
  Удобно, чтобы освободить место под большие PDF, не теряя то, что в них было.
- 🗑 **«Удалить книгу и базу»** — файл и фрагменты убираются вместе (как было).

### Как устроена индексация

Из файла достаётся текст по частям (страница PDF, глава EPUB, часть TXT), затем
из него убираются колонтитулы, мягкие переносы и разрывы слов. Числа остаются:
колонцифрой считается только одинокое число в самой верхней или самой нижней
строке страницы. Оглавления, предметные указатели, страницы без текста и
фрагменты с испорченным шрифтом в базу не записываются: толку от них нет, а
название блюда в указателе встречается десятки раз рядом с номерами страниц и
обгоняло сам рецепт.

Книга считается уже прочитанной, если её фрагменты есть в базе и файл с тех пор
не менялся (совпадают размер и время изменения). Изменили файл — он прочитается
заново; скан, прочитанный без распознавания, перечитается, когда включён OCR.
Всё это записано во фрагментах книги, а не в отдельном списке: перенос папки
`agents/` на другой компьютер ничего не теряет.

Служебный текст узнаётся по признакам, а не по конкретным книгам:

| Признак | Что находит |
|---|---|
| точки-заполнители («Борщ . . . . . 27») | оглавление |
| «название + номер страницы» подряд («177. Борщ», «Клафути 118») | предметный указатель |
| список названий без номеров: почти нет запятых и точек, много слов с большой буквы, нет глаголов приготовления | оглавление в книгах, где номера не распознались |
| испорченный шрифт (`/g299/g301`) | мусор распознавания |

Строчки ингредиентов («мука 200 г») под последний признак не попадают: они
пишутся со строчной буквы. Технологические карты — тоже: в них граммовки
напечатаны отдельными строками («Картофель», «80», «60»), и раньше эти строки
пропадали вместе с колонцифрами, из-за чего рецепт приходил в модель без
количеств. Теперь такие страницы узнаются по столбцам «брутто/нетто», номеру
рецептуры и строке «Расход сырья» и остаются в базе целиком.

## Запуск

```bash
python app.py
```

- На ПК: <http://localhost:8000>
- С телефона (тот же Wi-Fi): `http://<IP-ПК>:8000` → «Добавить на главный экран».
- Настройки — ⚙ в правом верхнем углу (агенты, книги, модели, база).
- Свой IP: `ipconfig` (Windows). При первом запуске разрешите доступ в фаерволе
  для **частных** сетей.
- Адрес для телефона, перезапуск и остановка сервера — там же, вкладка «Сервер»
  (⚙ → Сервер): он сам определяет IP компьютера в сети.

## Настройка (`config.yaml`)

| Блок | Что задаёт |
|---|---|
| `prompt` | общий промпт (если у агента своего нет), задание модели на промпт, шаблоны ответов |
| `store` | папка с агентами, форматы книг, размеры фрагментов, OCR |
| `embeddings` | локальная модель эмбеддингов |
| `llm` | провайдер, модель, параметры генерации и таймауты |
| `llamacpp` | свой llama-server: путь к нему, папка с GGUF, порт, ключи запуска |
| `search` | сколько фрагментов искать, лимит контекста, история, режим поиска, сведение источников |
| `server` | адрес и порт |

**Только этот ПК, без доступа по сети** — `server.host: 127.0.0.1`.

**Сменить тему** — промпт агента в ⚙ → Агенты (у каждого агента свой).
**Сменить модель** — `llm.model`. **Сменить провайдера** — `llm.provider`.

## Провайдеры моделей

Генерация работает через любой OpenAI-совместимый сервер. Встроены готовые
провайдеры (выбираются в ⚙ → Модели, ключ вводится там же):

| Провайдер | Ключ | Примечание |
|---|---|---|
| `ollama` | не нужен | локально, по умолчанию; модели — [ollama.com/search](https://ollama.com/search) |
| `llamacpp` | не нужен | [llama.cpp](https://github.com/ggml-org/llama.cpp) (`llama-server`) на `127.0.0.1:8080`, запуском занимается приложение |
| `groq` | `GROQ_API_KEY` | бесплатно, очень быстро |
| `gemini` | `GEMINI_API_KEY` | бесплатный тариф Google |
| `openrouter` | `OPENROUTER_API_KEY` | есть бесплатные модели |
| `deepseek` | `DEEPSEEK_API_KEY` | дешёвый API |
| `mistral` | `MISTRAL_API_KEY` | есть бесплатный тариф |
| `openai` | `OPENAI_API_KEY` | платно |

Ключ можно задать двумя способами:

1. **В интерфейсе** — ⚙ → Модели, кнопка «Ввести API-ключ»: выберите провайдера
   и вставьте ключ. Он сохранится в локальный файл `secrets.json` (в `.gitignore`).
2. **Переменной окружения** — например `set GROQ_API_KEY=...` (Windows).

### Список моделей

Список моделей тянется у самого провайдера (`/models`), поэтому он всегда
актуален: у провайдеров со временем появляются новые модели и убираются старые.
В поле модели видны модели выбранного провайдера, а ниже — бесплатные модели
остальных провайдеров (они подписаны «бесплатно»). Выбор пункта вида
`[groq] openai/gpt-oss-120b` автоматически переключает и провайдера, и модель.

Бесплатные определяются по цене из ответа провайдера (OpenRouter), по суффиксу
`:free`, по флагу провайдера (у Groq весь API бесплатный) и по имени модели
(например, `flash` у Gemini). Служебные модели — синтез речи, расшифровка
звука, эмбеддинги — из списка исключаются. Список моделей кэшируется на 5 минут
и обновляется при вводе ключа; кнопка «↻ Обновить список» в ⚙ → Модели просит
его заново — например, сразу после запуска llama-server или Ollama.

Любой свой сервер тоже подойдёт: укажите в `llm.provider` полный URL
(`http://192.168.1.5:1234/v1`) OpenAI-совместимого эндпоинта.

### llama.cpp и LM Studio

`llama-server` из [llama.cpp](https://github.com/ggml-org/llama.cpp) отдаёт тот
же OpenAI-совместимый API, поэтому в списке провайдеров он есть отдельным
пунктом `llama.cpp (локально, без ключа)` — с адресом `http://127.0.0.1:8080/v1`.
Ключ не нужен, как и у Ollama.

#### Своя модель прямо из интерфейса (консоль не нужна)

В ⚙ → Модели есть блок «llama.cpp»:

1. Положите файл `.gguf` в папку `models/` рядом с проектом (подпапки тоже
   видны, в списке они показываются как `подпапка/модель.gguf`).
2. Выберите модель и нажмите «Запустить».
3. Сервер поднимется на `127.0.0.1:8080`, провайдер `llama.cpp` станет
   активным, а выбранная модель — текущей. Можно сразу спрашивать.
4. Кнопка «Остановить» выключает сервер. Журнал (`Лог llama-server`) показывает,
   почему модель не поднялась.

Где взять `llama-server`:

- положите `llama-server.exe` в папку `llama.cpp/` рядом с проектом — приложение
  найдёт её сама;
- или укажите путь в `config.yaml` → `llamacpp.binary`;
- или оставьте `llama-server.exe` в PATH (например, установка через winget
  кладёт его туда).

Настройки в `config.yaml` → `llamacpp`:

```yaml
llamacpp:
  binary: ""        # пусто — ищем рядом с проектом и в PATH
  models_dir: "./models"
  port: 8080        # порт управляемого сервера; провайдер смотрит туда же
  args:             # дополнительные ключи llama-server
    - "-c"
    - "8192"
```

- `args` — место для `-ngl 99` (слои на GPU) и прочего. Контекст `8192` взят с
  запасом: при сведении источников в модель уходит около 16 000 символов.
- Сервер не привязан к приложению: перезапуск самого приложения его не
  останавливает, состояние переживает перезапуск.
- Если порт 8080 занят другой программой, приложение скажет об этом. Тогда
  либо освободите порт, либо укажите другой в `llamacpp.port` и перезапустите
  приложение — провайдер получит тот же адрес.

Запуск вручную по-прежнему работает:

```bash
llama-server.exe -m qwen2.5-3b-instruct-q4_k_m.gguf --port 8080 --alias qwen2.5-3b
```

- `--alias` — имя модели: под ним она появится в списке моделей. Без него там
  будет путь к файлу, и его тоже можно вписать в поле модели вручную.
- Порт по умолчанию у `llama-server` — 8080. Если он занят, запустите на другом
  и укажите провайдера полным URL: `http://127.0.0.1:8081/v1`.
- GGUF-модели берутся на [Hugging Face](https://huggingface.co/models?library=gguf).
  Для слабого CPU подойдут кванты `Q4_K_M` моделей 3B–8B: они занимают 2–5 ГБ
  и отвечают без GPU.
- Если сервер не запущен, интерфейс так и напишет: «Сервер не отвечает —
  проверьте, запущен ли он». Модель можно вписать в поле руками.
- LM Studio — графическая обёртка над llama.cpp: включите в ней локальный сервер
  (у него порт 1234) и укажите провайдера полным URL `http://127.0.0.1:1234/v1`.

### Подбор модели под слабое железо

Если GPU слабый (мало VRAM), 8B-модели считаются на CPU и отвечают медленно.
Варианты:

- лёгкие локальные: `qwen2.5:3b`, `gemma2:2b`, `llama3.2:3b`;
- либо генерация в облаке (Groq, Gemini, OpenRouter) — поиск и эмбеддинги
  остаются локальными, в облако уходит только найденный контекст;
- уменьшить `search.n_results` и `search.max_context_chars`; `max_tokens` тоже
  можно снизить — ответ станет короче, а если модели не хватит лимита, сервер
  допишет продолжение;
- `search.lexical` (по умолчанию `true`) даёт приоритет точным совпадениям по
  словам; поиск идёт через индекс Chroma и потому быстрый. Отключение ускоряет
  ещё немного, но теряет точные совпадения.

## Качество поиска

Найденные фрагменты идут в модель целиком: разрезанный пополам фрагмент
бесполезен, поэтому лимит `search.max_context_chars` отбрасывает целые
фрагменты, а не обрывает текст на середине.

Длина ответа ограничена `llm.max_tokens` (по умолчанию 4096): подробный
ответ по-русски занимает около 2600 токенов, поэтому на 2000 он обрывался
на полуслове. Если модель всё равно упёрлась в лимит, сервер замечает это по
`finish_reason` и сам просит продолжение — до `llm.max_continuations` раз
(по умолчанию 2). Дописывание видно в чате строкой «⏳ Ответ длинный —
дописываю продолжение…».

## Лимиты бесплатных тарифов

У бесплатных облачных моделей ограничена не только скорость, но и объём:
например, у Groq это **8000 токенов в минуту**. Один вопрос со сведением
(контекст из книг ~6000 токенов + ответ) занимает почти всю минуту, поэтому
второй вопрос подряд может получить ответ «Rate limit reached». Это лимит
провайдера, а не ошибка сервера: подождите минуту (в сообщении указано
сколько) или выберите модель с большим лимитом.

Если упираетесь в лимит постоянно, уменьшите `search.merge_context_chars`
(сколько текста уходит на сведение) или отключите сведение.

### Сведение ответов из разных книг

Обычно один и тот же материал описан в нескольких книгах — с разными
подробностями. В обычном режиме модель видит только несколько лучших
фрагментов, поэтому может выдать обрывок или общие слова вместо полного
ответа.

Включается в ⚙ → Книги → «Сводить ответы из разных книг» (или строкой
`search.merge_mode` в `config.yaml`):

| Режим | Что происходит | Когда включать |
|---|---|---|
| **Выкл** | как раньше: что нашли, то и в ответе | по умолчанию, быстрее всего |
| **Быстро** | поиск берёт лучший фрагмент из каждой из нескольких книг, модель сама сводит их в один связный ответ | когда ответ ищется в разных книгах |
| **Точно** | два прохода: сначала черновик-слияние всех вариантов, потом ответ по нему | когда нужен цельный ответ и время ожидания не важно |

Режим «Точно» отвечает примерно вдвое дольше: два обращения к модели вместо
одного. Сколько книг опрашивать — `search.merge_sources` (по умолчанию 6),
сколько текста отдать на сведение — `search.merge_context_chars`.

Локальной модели на CPU нужно время: обычному ответу хватает `llm.timeout`
(300 секунд), а сведению — `llm.merge_timeout` (900). Если вместо ответа
приходит «модель не ответила за отведённое время» — поднимите это число в
`config.yaml` или уменьшите `search.merge_context_chars`.

Промпты сведения можно переписать в `config.yaml` — ключи `prompt.merge_template`,
`prompt.synthesis_template`, `prompt.answer_from_draft_template` (по умолчанию
они заданы в `config.py` и подходят любой теме: рецептам, даташитам, договорам).
Промпт самого агента задаётся отдельно — он живёт у агента, см.
[«Промпт агента»](#промпт-агента).

Оглавления, предметные указатели и мусор распознавания в базу теперь не
попадают вовсе — их отсеивает `core/parsers.py` при индексации. На всякий случай
те же правила применяются и при поиске: если в базе остались старые фрагменты,
они отодвигаются в конец результатов, но в ответ попадают, только если ничего
лучше не нашлось.

Таблица рецептуры (столбцы «брутто/нетто», «Расход сырья») служебным текстом не
считается ни при индексации, ни при поиске: числа в ней — граммовки, и именно
этот фрагмент отвечает на вопрос «сколько класть». Отдельно поощряется
совпадение по всем словам вопроса: на «московский борщ» технологическая карта,
где есть и «борщ», и «московский», идёт впереди биографии шефа, где есть только
«московский», даже если биография поднялась в векторном списке.

Если книга распознана плохо, помогут два шага: включить `store.ocr: auto`
(распознаёт страницы-картинки через tesseract) и переиндексировать базу заново.
Поиск сам по себе испорченный текст не исправит.
